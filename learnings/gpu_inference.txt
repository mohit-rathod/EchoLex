| --max-num-batched-tokens  | Maximum number of tokens that can be processed in a single iteration                          |
|                           |   * across all active sequences in a single model forward pass.                               |
|                           |   * across all active sequences in a single model forward pass.                               |

|                           |   * use eager-mode PyTorch execution and disable CUDA graphs.                                 |

** Inference Request parameters**
| Parameter               | Meaning                                                                                                        |
| ----------------------- | -------------------------------------------------------------------------------------------------------------- |
| `model`                 | Model name exposed by the server, e.g. `qwen3-4b-awq`.                                                         |
| `messages`              | Conversation history containing `system`, `user`, and `assistant` messages.                                    |
|                         |     * System: It acts as the "meta-instructions" or "root prompt" for the LLM.                                 |
|                         |     * User: It represents the immediate input that the model needs to process or answer                        |
|                         |     * Assistant: It maintains conversational continuity by feeding past assistant responses back into the API. |
| `temperature`           | Controls randomness. Lower = more deterministic; higher = more varied.                                         |
| `top_p`                 | Nucleus sampling. Restricts generation to tokens covering the specified cumulative probability.                |
| `max_completion_tokens` | Maximum number of tokens the model may generate.                                                               |
| `frequency_penalty`     | Penalizes tokens according to how often they have already appeared; reduces repetition.                        |
| `presence_penalty`      | Penalizes tokens once they have appeared at all; encourages introducing new content.                           |
| `stop`                  | String(s) that cause generation to stop when encountered.                                                      |
| `stream`                | `true` sends generated tokens/chunks progressively instead of waiting for the full answer.                     |
| `n`                     | Number of alternative completions to generate. Usually `1`.                                                    |
| `seed`                  | Attempts to make sampling more reproducible, where supported.                                                  |
| `logprobs`              | Returns token log-probabilities when supported.                                                                |
| `tools`                 | Defines functions/tools the model is allowed to call.                                                          |
| `tool_choice`           | Controls whether/how the model should use provided tools.                                                      |
| `response_format`       | Constrains output format, such as structured JSON where supported.                                             |


**CUDA Graph**
    Normally, during inference, PyTorch launches many CUDA kernels from the CPU:
    CPU
    │
    ├─ launch kernel 1 ──► GPU
    ├─ launch kernel 2 ──► GPU
    ├─ launch kernel 3 ──► GPU
    ├─ launch kernel 4 ──► GPU
    │
    ...

    Every kernel launch has CPU-side overhead. For an LLM decoding one token at a time, that overhead can matter because the same pattern of GPU operations repeats again and again.

    A CUDA Graph captures that repeated GPU workload once and later iterations can replay the whole graph:

    kernel 1
    kernel 2
    kernel 3
    kernel 4
    │
    ▼
    CUDA Graph

    CPU
    │
    └─ replay graph ─────► GPU
                        ├─ kernel 1
                        ├─ kernel 2
                        ├─ kernel 3
                        └─ kernel 4

    The biggest benefit is generally lower latency and less CPU launch overhead, especially during autoregressive decode where the model repeatedly executes very similar operations.


**Eager Execution**
    Eager execution means PyTorch runs operations normally as they are encountered:
    Each operation causes normal runtime dispatch/kernel launches.

    Conceptually:

    Python / PyTorch
        │
        ▼
    operation
        │
        ▼
    CUDA kernel
        │
        ▼
    next operation
        │
        ▼
    CUDA kernel

    This is more flexible because execution can change dynamically.


**What does --enforce-eager do?**
    vllm serve ... --enforce-eager

    effectively changes:

    Default:

    vLLM
    │
    ├─ CUDA Graph where possible
    │
    └─ eager execution where necessary

    into:

    vLLM
    │
    └─ eager execution only


**Why --enforce-eager?**
    1. Debugging
    2. Model compatibility
    3. Lower startup/capture complexity
    4. Memory considerations


**Prefill & Decode**
    *Prefill*

        Prefill is when the model processes the entire input prompt before generating the first new token.
        uring prefill, the model processes all prompt tokens together:

        Prompt tokens
        │
        ▼
        Transformer layers
        │
        ▼
        KV cache created
        │
        ▼
        probability for first output token

        So prefill is roughly:

            input tokens → model → build KV cache

        Prefill is usually:

            highly parallel
            compute-heavy
            dominated by matrix multiplications
            sensitive to prompt length

        A 5000-token prompt takes much more prefill work than a 50-token prompt.
        This phase determines much of the time to first token (TTFT).

    *Decode*

        Decode begins after prefill.

        Now the model generates output one token at a time.

        For example:

        The
        The transformer
        The transformer model
        The transformer model uses
        ...

        At each step:

            previous token
                +
            KV cache
                │
                ▼
            model
                │
                ▼
            next token

        The important thing is that the model does not reprocess the entire original prompt every time.
        It reuses the KV cache generated during prefill.
